# SCF 2026.1.1 Pivot — Design Spec

**Date:** 2026-05-11
**Status:** Draft — awaiting Peter's review
**Supersedes:** `docs/superpowers/plans/2026-05-11-pnpm-seed.md` (Phase 2 of this spec replaces that plan's Tasks 1–14)

---

## Goal

Replace graphletter's ad-hoc `data/` CSV pile with a **vendored upstream SCF XLSX as the single source of truth**, pivot the seed pipeline onto deterministic extractions from that XLSX, and migrate prod from SCF 2025.1.1 → 2026.1.1. Public OSS repo ships with a correct, defensible CC BY-ND 4.0 license posture verifiable offline by any reviewer.

## Why pivot

The existing approach (`docs/superpowers/plans/2026-05-11-pnpm-seed.md` and `scripts/scf-license-audit.ts`) classifies file provenance from git history. graphletter's OSS repo was cut as a fresh `chore: initial commit (v0.1.0)`, so `data/` has exactly one commit — meaning the audit is structurally incapable of distinguishing upstream-unmodified files from graphletter-authored ones. The current `data/LICENSE_AUDIT.json` labels `controls.csv` (an 8.7 MB verbatim upstream catalog) as `graphletter-authored`. Shipping that publicly is a license-posture misrepresentation.

The pivot answers the right question — "do our bytes match upstream's bytes?" — by treating the upstream XLSX as the source of truth and deriving everything from it.

## Architecture

```
data/secure-controls-framework-scf-2026-1-1.xlsx
        │   (verbatim CC BY-ND redistribution; sha256 pinned)
        ▼   scripts/extract-scf.ts          ← deterministic, idempotent
data/{controls,domains-and-principles,...}.csv
        │   (sha256 pinned in data/PROVENANCE.json)
        ▼   scripts/verify-scf-extraction.ts ← pre-commit + CI
data/LICENSE_AUDIT.json + data/README.md (regenerated)
        │
        ▼   scripts/seed-all.ts
fork's clean Supabase project, fully seeded
        │
        ▼   supabase/migrations/<timestamp>_upgrade_scf_to_2026_1_1.sql
prod (gbnxwsntyzyrpwmjaaqa) bumped from 2025.1.1 → 2026.1.1
```

### Extractor

- `scripts/extract-scf.ts`:
  - Inputs: `data/secure-controls-framework-scf-2026-1-1.xlsx`.
  - Outputs: 7 canonical CSVs (the 7 currently-consumed sheets) + 2 deferred CSVs (Phase 4 sheets, attested but unused).
  - Deterministic: identical XLSX → identical CSV bytes across runs and machines (uses `xlsx` or `exceljs`, then re-emits with `csv-stringify` and explicit options: LF line endings, RFC 4180 quoting, no BOM, UTF-8).
  - Idempotent: re-running over committed CSVs produces no diff.
  - Updates `data/PROVENANCE.json` sha256 fields on the `xlsx-extract` entries.

### Verifier (replaces `scripts/scf-license-audit.ts`)

- `scripts/verify-scf-extraction.ts`:
  - Re-extracts XLSX to a temp directory.
  - Byte-compares each temp CSV to its committed counterpart in `data/`.
  - For `graphletter-authored` / `documentation` entries: confirms current sha256 matches manifest.
  - For the `xlsx-extract` entries: confirms current sha256 matches manifest AND that the re-extract bytes match the committed bytes.
  - Confirms `xlsx` sha256 matches `data/PROVENANCE.json`.
  - Emits `data/LICENSE_AUDIT.json` (per-file verdict block) and regenerates `data/README.md` (human-readable attribution table).
  - Exit codes: 0 if all green, 2 if any mismatch.
- Hook integration: pre-commit (`scripts/pre-commit.sh`) runs `pnpm verify:scf-extraction` whenever `data/` or `scripts/extract-scf.ts` changes.

### Seed orchestrator

- `scripts/seed-all.ts`:
  - Reads `data/*.csv` (canonical extracts) and graphletter-authored CSVs.
  - Writes to a fresh Supabase project via `@supabase/supabase-js` with the service role key.
  - Steps:
    1. `scf_principles` + `scf_domains` — from `data/domains-and-principles.csv`.
    2. `scf_authoritative_sources` + `scf_frameworks` — from `data/authoritative-sources.csv`.
    3. `scf_controls` + `scf_control_mappings` — from `data/controls.csv`.
    4. `scf_risks` + `scf_control_risk_mappings` — from `data/risks.csv`.
    5. `scf_threats` + `scf_control_threat_mappings` — from `data/threats.csv`.
    6. `scf_maturity_levels` — from `Lists` enum sheet or static (decide during Phase 2).
    7. `scf_evidence_request_list` — from `data/evidence-request-list.csv`.
    8. `scf_assessment_objectives` — from `data/assessment-objectives.csv`.
    9. `scf_control_evidence_mappings` — derived (ERL JSON arrays × controls join).
    10. `scf_control_integrations` — seeded via `supabase/migrations/<ts>_seed_scf_control_integrations.sql` (4 graphletter rows).
  - Per-step row-count summary printed; exit non-zero on any failure.
- `scripts/seed-verify.ts`:
  - Reads `data/seed/expected_row_counts.json` (snapshot generated from a freshly-seeded sandbox at 2026.1.1).
  - Queries each table; asserts within ±1 % tolerance.
  - Exit non-zero on any out-of-tolerance.
  - **Bootstrap order:** Phase 2 must seed the sandbox _once_ to capture the expected-row-counts snapshot before committing it. The first seed run cannot verify itself; subsequent runs do.

### Prod migration (Phase 3)

- `scripts/diff-scf-versions.ts`:
  - Compares prod's 2025.1.1 state (via MCP `execute_sql`) to the 2026.1.1 extracted CSVs.
  - For each SCF table: emits added IDs, removed IDs, changed rows.
  - Outputs `migrations-staging/scf-2026-1-1-diff.json` for human review.
- `scripts/check-scf-deletion-safety.ts`:
  - For each removed ID, scans every table in prod for FK references to that ID (uses `information_schema.referential_constraints`).
  - Emits two lists: `safe-to-delete` (no inbound FKs reference it) vs `requires-decision` (inbound FKs exist).
  - **Hard-delete is the intent.** Per Peter's design call: if any removed ID has live customer-authored FK references, the migration ABORTS and we resolve case-by-case before proceeding.
- `supabase/migrations/<ts>_upgrade_scf_to_2026_1_1.sql`:
  - `INSERT ... ON CONFLICT (id) DO UPDATE` for net-new and changed rows.
  - `DELETE FROM <table> WHERE id IN (<removed-ids>)` for IDs not in 2026.1.1.
  - Wrapped in a single transaction; FK violations abort the entire migration.
- Pre-flight: `pg_dump`-style Supabase point-in-time snapshot before applying.
- Post-apply: rerun `pnpm seed:verify` against prod with the 2026.1.1 row-count snapshot.

### Documentation

- `SEEDING.md` — fork-setup walkthrough (`pnpm dlx supabase db push && pnpm seed && pnpm seed:verify`).
- `data/README.md` — auto-generated attribution + per-file classification (replaces the current handwritten one).
- `data/LICENSE_AUDIT.json` — machine-readable audit verdict (regenerated each run).
- `AGENTS.md` — points at `pnpm seed` + `SEEDING.md`; deprecates `scripts/import-scf-data.js`.

### Phase 4 — Deferred

The two new 2026.1.1 sheets (Compensating Controls, Data Privacy Mgmt Principles) are **out of scope for this project**. They are extracted to CSV in Phase 1 (so they're attested + redistributable) but not seeded to tables. Revisit when product demand for these surfaces.

## Constraints

- **CC BY-ND 4.0:** Upstream XLSX is redistributable only as the original work, with attribution. Deterministic CSV extraction is a mechanical reformatting, not a derivative work — the verifier's reproducibility argument is the legal anchor.
- **Prod safety:** Phase 3 requires a Supabase backup before applying; hard-delete is gated on "no inbound customer FK references" (otherwise abort).
- **No `--no-verify`, no `SKIP_SPEC_CHECK=1`** in any commit.
- **Never commit `.env.*` or service-role keys.**
- **Sandbox-first:** every script change is exercised against a sandbox Supabase project before prod (using the sandbox Task 1 of the old plan provisions).

## Out of scope

- New tables / app surface area for the two Phase 4 sheets.
- Replacing the in-app SCF uploader UI (continues to work; eventually deprecated by `pnpm seed` but not removed in this project).
- Multi-version vendoring (only 2026.1.1 is the source of truth; old 2025.1.1 data exits with the prod migration).
- Backwards compatibility shims for `data/full_scf.csv` etc. — deleted outright; consumers updated to use `data/controls.csv`.
- File-naming convention overhaul (`Title Case.csv` → `kebab-case.csv`) beyond the canonical names listed in the Sheet→CSV mapping table above. Existing snake_case / Title Case names are grandfathered where they exist; only the duplicates listed under Phase 1 are deleted.

## Open risks

1. **FK landscape for removed IDs** (Phase 3): unknown until `check-scf-deletion-safety.ts` runs. If customers have evidence rows referencing controls that 2026.1.1 removed, hard-delete will block. Mitigation: dry-run + manual triage.
2. **Maturity-levels sheet identification:** the XLSX has a `Lists` sheet but no obvious `Maturity Levels` sheet. Phase 2 must locate the source of `scf_maturity_levels` rows in the XLSX (likely embedded in `Lists` or in `SCF 2026.1` as a column).
3. **Determinism of XLSX extraction:** ordering of rows in an XLSX sheet is generally stable, but cells with whitespace / hidden formula values may produce nondeterministic CSV output across `xlsx` library versions. Mitigation: pin `xlsx` library version; commit a fixture-based test that asserts byte-stable output.
4. **In-app uploader path coexistence:** `app/api/scf/import/route.ts` writes to the same tables `pnpm seed` writes to. After Phase 2, the two flows must not race or produce divergent state. Mitigation: route.ts is documented as "legacy uploader, prefer pnpm seed"; behavior is unchanged.
